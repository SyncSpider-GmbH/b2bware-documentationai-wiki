## Overview

All DataHub hubs use `CommonFilterRepository` for MongoDB-compatible filtering via Spatie QueryBuilder. Filters are passed as JSON-encoded arrays of condition objects in query parameters.

<Callout kind="info">
Each hub page documents its specific filterable fields. This page covers the generic filter syntax and operators that apply across all hubs.
</Callout>

## Filter Syntax

```
?filter[field_name]=[{"condition":"operator","value":"value"}]
```

The value is a JSON-encoded array of condition objects. Each condition object has:

| Key | Required | Description |
|-----|----------|-------------|
| `condition` | Yes | The comparison operator |
| `value` | Depends | The value to compare against (not needed for `EMPTY`/`NOT EMPTY`) |
| `operator` | No | Logical operator to combine with previous conditions (`AND` or `OR`) |

## Supported Operators

| Condition | Description | Example |
|-----------|-------------|---------|
| `=` | Exact match | `?filter[status]=[{"condition":"=","value":"active"}]` |
| `!=` | Not equal | `?filter[status]=[{"condition":"!=","value":"deleted"}]` |
| `>` | Greater than | `?filter[price]=[{"condition":">","value":100}]` |
| `<` | Less than | `?filter[price]=[{"condition":"<","value":500}]` |
| `>=` | Greater than or equal | `?filter[quantity]=[{"condition":">=","value":10}]` |
| `<=` | Less than or equal | `?filter[quantity]=[{"condition":"<=","value":100}]` |
| `LIKE` | Pattern match | `?filter[name]=[{"condition":"LIKE","value":"%search%"}]` |
| `IN` | Value in set | `?filter[status]=[{"condition":"IN","value":["active","pending"]}]` |
| `NOT IN` | Value not in set | `?filter[status]=[{"condition":"NOT IN","value":["canceled"]}]` |
| `EMPTY` | Field is null/empty | `?filter[description]=[{"condition":"EMPTY"}]` |
| `NOT EMPTY` | Field is not null/empty | `?filter[description]=[{"condition":"NOT EMPTY"}]` |

## Filter Field Types

| Type | Description | Example Values |
|------|-------------|----------------|
| `number` | Integer or float values | `1`, `42`, `3.14` |
| `text` | String values | `"Product Name"`, `"SKU-001"` |
| `date` | Date/DateTime values | `"2024-01-01"`, `"2024-01-01T10:30:00"` |
| `bool` | Boolean values | `true`, `false`, `1`, `0` |

## Combining Conditions

### AND Conditions

Multiple conditions on the same field can be combined with `AND` to create range filters:

<Request tabs="cURL">
```bash
# Price between 100 and 500
curl -s -X GET \
  'https://api.datahub.syncspider.com/api/v1/apps/product-hub/products?filter[price]=[{"condition":">=","value":100},{"condition":"<=","value":500,"operator":"AND"}]' \
  -H 'Authorization: Bearer {token}' \
  -H 'Accept: application/json'
```
</Request>

### OR Conditions

Use `OR` to match any of several values:

<Request tabs="cURL">
```bash
# Status is active OR pending
curl -s -X GET \
  'https://api.datahub.syncspider.com/api/v1/apps/customer-hub/customers?filter[status]=[{"condition":"=","value":"active"},{"condition":"=","value":"pending","operator":"OR"}]' \
  -H 'Authorization: Bearer {token}' \
  -H 'Accept: application/json'
```
</Request>

<Callout kind="tip" title="IN vs OR">
For matching multiple values on the same field, prefer the `IN` operator over chaining multiple `OR` conditions. It's more concise and performs the same operation.
</Callout>

## Relation Filters

Filter through relationships using dot notation. This allows you to filter a resource based on the properties of its related entities:

```
?filter[company.name]=[{"condition":"LIKE","value":"%Acme%"}]
```

<Request tabs="cURL">
```bash
# Find customers whose company name contains "Acme"
curl -s -X GET \
  'https://api.datahub.syncspider.com/api/v1/apps/customer-hub/customers?filter[company.name]=[{"condition":"LIKE","value":"%Acme%"}]&include=company' \
  -H 'Authorization: Bearer {token}' \
  -H 'Accept: application/json'
```
</Request>

## Callback / Search Filters

Some hubs define callback filters that query across multiple fields simultaneously. The most common is `search`:

```
?filter[search]=term
```

<Callout kind="info">
Callback filters use simple key-value syntax (not the JSON array format). Each hub documents which callback filters are available and which fields they search.
</Callout>

## Multiple Filters

Combine filters across different fields by adding multiple `filter[]` parameters. All filters are applied with AND logic:

<Request tabs="cURL">
```bash
# Public products created in 2024 with stock
curl -s -X GET \
  'https://api.datahub.syncspider.com/api/v1/apps/product-hub/products?filter[status]=[{"condition":"=","value":"public"}]&filter[_created_at]=[{"condition":">=","value":"2024-01-01"}]&filter[without_stock]=1' \
  -H 'Authorization: Bearer {token}' \
  -H 'Accept: application/json'
```
</Request>

## ProductHub Attribute Filter

ProductHub has a special `attribute` filter that uses the `AttributeFilterRepository` for advanced attribute-based product filtering:

```
filter[attribute]=[{"attribute_id":1,"attribute_value":"Red","condition":"IN","operator":"AND"}]
```

| Field | Values | Description |
|-------|--------|-------------|
| `attribute_id` | number | The attribute definition ID |
| `attribute_value` | string | Value(s) to match — comma-separated for multi-value |
| `condition` | `IN`, `NOT_IN`, `EQUALS`, `NOT_EQUALS`, `LIKE`, `GT`, `LT`, `GTE`, `LTE` | Match condition |
| `operator` | `AND`, `OR` | How to combine with other attribute conditions |

For full details, see [ProductHub Filters](/hubs/product-hub#filters).

## Sorting & Filtering by Custom Attribute Code

AttributesHub exposes two boolean flags that let any custom attribute participate as a first-class column on admin listing endpoints:

| Flag | What it unlocks |
|------|-----------------|
| `use_for_sorting` | `?sort=<attribute_code>` and `?sort=-<attribute_code>` on every endpoint whose target's group type matches the attribute's group |
| `use_for_admin_filtering` | `?filter[<attribute_code>]=[{...}]` on the same endpoints, using the same JSON filter shape as native fields |

Both flags drive a denormalized field on the underlying document, so sorting and filtering are O(1) per row — no joins, no per-row PHP work.

### Endpoints that support it

`use_for_sorting` and `use_for_admin_filtering` are honored on:

- `GET /api/v1/apps/product-hub/products` (group type: `product`)
- `GET /api/v1/apps/product-hub/categories` (group type: `category`)
- `GET /api/v1/apps/customer-hub/customers` (group type: `customer`)
- `GET /api/v1/apps/customer-hub/companies` (group type: `company`)
- `GET /api/v1/apps/order-hub/orders` (group type: `order`)

### Discovery — list the catalogue

Before binding the dynamic columns to a UI (sort dropdown, filter picker), fetch the catalogue from the AttributesHub list endpoint:

```
GET /api/v1/apps/attributes-hub/attributes
    ?filter[use_for_sorting]=[{"condition":"=","value":"true"}]
    &filter[group.type]=[{"condition":"=","value":"product"}]
    &include=translation
    &per_page=200
```

Swap `use_for_sorting` for `use_for_admin_filtering` to discover filterable attributes; swap `group.type` for the target group (`product`, `category`, `customer`, `company`, `order`).

Each row carries `id`, `attribute_code`, `name`, `type`, and (with `include=translation`) localized labels.

### Examples

```bash
# Sort products by the EAN attribute, descending
GET /api/v1/apps/product-hub/products?sort=-ean

# Filter customers by loyalty_tier NOT EMPTY
GET /api/v1/apps/customer-hub/customers?filter[loyalty_tier]=[{"condition":"NOT EMPTY","value":"true"}]

# Filter orders by p_o_number = "12345"
GET /api/v1/apps/order-hub/orders?filter[p_o_number]=[{"condition":"=","value":"12345"}]
```

### Native vs. dynamic collisions

If an `attribute_code` collides with a native sort or filter (e.g. `email`, `sku`, `name`), the **native column wins** — the dynamic entry is silently skipped. Pick unique attribute codes if you want them to be exposed as columns.

### Difference from `use_in_search` and `show_in_cart`

Two related flags do **not** participate in `?sort=` / `?filter[]=`:

- `use_in_search` widens the existing `?filter[search]=…` callback on `GET /products` to also match against the attribute's stored values (alongside `name` and `sku`).
- `show_in_cart` is a pure display flag — it surfaces the attribute on the storefront cart line; there is no API surface keyed off it beyond the catalogue discovery above.

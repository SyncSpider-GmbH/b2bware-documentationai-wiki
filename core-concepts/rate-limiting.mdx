---
title: Rate Limiting
description: Per-scope API rate limits, default ceilings, how each scope is counted, and 429 behaviour for the DataHub API.
---

The DataHub API applies **per-scope** rate limits. Traffic is classified into
scopes (admin, integration, storefront, webhook, auth, bulk, public) and each
scope has its own request-per-minute ceiling and its own way of counting
requests, so unrelated tenants and users never share a single rate-limit bucket.

## Scopes

Defaults are requests **per minute**.

| Scope | Applies to | Default | Counted per |
|-------|------------|---------|-------------|
| `admin` | Authenticated admin API (`/api/v1/apps/*`) | `300` | Authenticated **user** (unauthenticated requests: per IP, at the `public` ceiling) |
| `integration` | Machine-to-machine integration API (`/apiv1/*`, excluding `/apiv1/internal/apps/*`) used by integration platforms to sync datasets | `3000` | Authenticated **user** (unauthenticated requests: per IP, at the `public` ceiling) |
| `bulk` | Bulk, export and import operations on the admin API (paths with a `bulk`, `export` or `import` segment) | `60` | Authenticated **user** (IP fallback) |
| `storefront` | Server-rendered storefront pages | `120` | Shop **customer** → browser **session** → IP |
| `storefront_action` | Storefront account actions such as generating, rotating or deleting a catalog export | `10` | Shop **customer** → browser **session** → IP |
| `webhook` | Public payment / provider webhooks (`/api/v1/webhooks`, routes carrying an installation key) | `120` | **Installation key** in the URL (IP fallback) |
| `embed` | Integration Hub embed bootstrap and token refresh | `20` | IP **and** installation key |
| `auth_login` | Unauthenticated login | `30` | IP |
| `auth_register` | Unauthenticated registration | `10` | IP |
| `password_reset` | Forgot-password and password reset | `5` | IP |
| `public` | Generic public (unauthenticated) endpoints | `60` | IP |

## How Requests Are Counted

Each scope counts requests so that one caller cannot exhaust the budget of
unrelated callers:

- **Authenticated scopes** (`admin`, `integration`, `bulk`) count per
  **authenticated user**. A shared office or VPN IP therefore does not
  throttle a whole team — each user gets their own budget.
- **Auth scopes** (`auth_login`, `auth_register`, `password_reset`) count per
  **IP**, because there is no identity yet.
- **Webhooks** count per **installation key** in the URL, so one payment
  provider calling many stores never starves another store's webhooks.
- **Storefront** scopes count per signed-in customer, otherwise per browser
  session, so shoppers behind one shared network do not share a budget.

<Callout kind="info" title="Endpoint limits win">
Some endpoints declare their own, usually stricter, limit (for example theme
uploads, custom-domain verification, or storefront cart and checkout actions).
That limit applies instead of the scope default. Static storefront assets
(`assets/*`) are not counted against the page budget, so a page load cannot
throttle its own assets.
</Callout>

<Callout kind="info" title="Integration traffic has its own budget">
The `/apiv1/*` surface is machine-to-machine traffic: integration platforms
sync whole datasets through it, often at a rate no human admin would ever
produce. It therefore has its own high-ceiling `integration` scope — bulk
paths under it included — so a running sync never competes with the admin UI.
Custom app packages under `/apiv1/internal/apps/*` serve admin UIs, so they
keep the admin / bulk classification.
</Callout>

Ceilings are configured per environment. If an integration genuinely needs
more headroom, contact support with the scope and the expected request rate.

## 429 Behaviour

When a scope's ceiling is exceeded, the API responds with **HTTP 429 Too Many
Requests**. The response carries standard rate-limit headers so clients can back
off gracefully:

| Header | Meaning |
|--------|---------|
| `Retry-After` | Seconds to wait before retrying. |
| `X-RateLimit-Limit` | The ceiling for the current scope. |
| `X-RateLimit-Remaining` | Requests remaining in the current window. |

```json
{
  "message": "Too Many Attempts."
}
```

<Steps>
  <Step title="Respect Retry-After">
    On a 429, wait the number of seconds in the `Retry-After` header before
    retrying. Do not retry immediately in a tight loop.
  </Step>
  <Step title="Back off and spread load">
    Use exponential backoff with jitter for bulk and import workflows, and
    stay under the `bulk` ceiling by batching requests.
  </Step>
  <Step title="Authenticate every request">
    Authenticated admin and bulk traffic is counted per user, so it does not
    share an IP budget with the rest of your team.
  </Step>
</Steps>

<Callout kind="warning" title="High-volume webhook tenants">
Payment providers **retry webhooks on a 429**, and repeated throttling can delay
order-status updates for your customers. If a store receives a very high volume
of provider webhooks, contact support so the webhook ceiling can be raised.
</Callout>

For a detailed backoff loop, request-volume audit, and common pitfalls, see the

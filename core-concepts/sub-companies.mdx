---
title: "Sub-Companies"
description: "Create a sub-company under an agency tenant, provision its hub installations, and verify the setup with a settings call."
---

Some tenants are **agencies**: a parent company that manages multiple client shops. Each client shop is a **sub-company** — a fully separate tenant with its own hub installations, installation keys, and data, linked to the parent via `parent_company_id`.

This page walks through the full API flow: create the sub-company, provision its hubs, and confirm everything works with a final settings request.

<Callout kind="info" title="Two services are involved">
Companies live on the **user service** (SpiderDesk) — DataHub itself has no company-c
    reation endpoint. The sub-company is created on the user service, and DataHub sees it immediately (it reads companies straight from the user service). DataHub then binds hub installations to that company id. There is no propagation step in either direction.
</Callout>

## Prerequisites

Before you start, make sure all of the following are true — each one is validated by the API and the request fails otherwise:

| Requirement | Failure if not met |
|---|---|
| The parent company has agency features enabled (`is_agency = true`) | `400` — "Company does not support agency features, or user does not have an access to agency" |
| The parent company's subscription plan has a free sub-account slot (`numberOfSubAccounts`) | `400` — "Company can have maximum of N. Please update subscription plan." |
| You have a user service bearer token for a user with access to the parent company | `401` / `403` |

You will also need the numeric **parent company id** and your **user id** (both visible in the admin panel, or via `GET {USER_SERVICE_URL}/api/v1/users/me`).

<Callout kind="warning" title="Base URLs differ per step">
Steps 1–2 run against the **user service** (`{USER_SERVICE_URL}`, e.g. `https://desk.syncspider.com`). Steps 3–5 run against **DataHub** (`https://api.datahub.syncspider.com`). Your DataHub administrator provides the user service URL for your environment.
</Callout>

## Step 1 — Create the Sub-Company

Call the user service with the **parent** company id in the path:

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X POST \
      '{USER_SERVICE_URL}/api/v1/companies/123/createSubCompany' \
      -H 'Authorization: Bearer YOUR_DESK_TOKEN' \
      -H 'Accept: application/json' \
      -H 'Content-Type: application/json' \
      -d '{
        "name": "Acme Client Shop",
        "billing_agency": true
      }'
    ```
  </Tab>
</Tabs>

Accepted body fields:

| Field | Type | Notes |
|---|---|---|
| `name` | string | Display name of the sub-company. |
| `billing_agency` | bool | `true` = the agency is billed for this sub-company. When `false`, the sub-company starts on its own trial plan. |
| `meta_data` | object, nullable | Free-form metadata. |
| `extra_attributes` | array, nullable | Items of `{ "platform_id": int, "attribute": string }`. |
| `invitations` | array, nullable | Items of `{ "platform_id": int, "email": string, "role": "user"\|"admin" }` — each entry sends a membership invitation email. |

`owner_id`, `parent_company_id`, `is_agency`, and `is_erp` are **prohibited** — the API sets ownership and the parent link itself, and a sub-company can never be an agency.

The response is the created company object. Note its `id` — you need it in every following step:

```json
{
  "id": 456,
  "name": "Acme Client Shop",
  "parent_company_id": 123,
  "owner_id": 42,
  "is_agency": false
}
```

All members of the parent agency company are automatically added to the sub-company with the same roles they hold in the agency.

## Step 2 — Switch Your Active Company

DataHub's installation endpoints resolve the target company from the calling user's **current company**. Point it at the new sub-company:

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X PUT \
      '{USER_SERVICE_URL}/api/v1/users/42' \
      -H 'Authorization: Bearer YOUR_DESK_TOKEN' \
      -H 'Accept: application/json' \
      -H 'Content-Type: application/json' \
      -d '{ "current_company_id": 456 }'
    ```
  </Tab>
</Tabs>

<Callout kind="warning" title="Do not skip this step">
If you leave `current_company_id` on the parent company, step 3 installs the hubs into the **parent** tenant instead of the sub-company.
</Callout>

## Step 3 — Install Hubs for the Sub-Company

Every hub (ProductHub, OrderHub, SettingsHub, …) must be installed per company. Installation creates the company's own entities and — crucially — generates the **installation key** used for all storefront API calls.

First list the available application templates to get their ids:

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X GET \
      'https://api.datahub.syncspider.com/apiv1/internal/templates?filter[type]=application' \
      -H 'Authorization: Bearer YOUR_DESK_TOKEN' \
      -H 'Accept: application/json'
    ```
  </Tab>
</Tabs>

Then install each application you need by template id:

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X PUT \
      'https://api.datahub.syncspider.com/apiv1/internal/templates/install/17' \
      -H 'Authorization: Bearer YOUR_DESK_TOKEN' \
      -H 'Accept: application/json'
    ```
  </Tab>
</Tabs>

Notes:

- The token must carry **read/write** API permission — read-only tokens get `403`.
- Declared hub dependencies are installed recursively, so installing a hub also installs the hubs it depends on.
- Installing an application that is already installed for the current company returns `400` — "application is already installed" (safe to treat as success when re-running).
- Templates in `draft` status cannot be installed.

At minimum, install **SettingsHub** — the verification step below depends on it. A typical shop also needs ProductHub, OrderHub, CustomerHub, MediaHub, and AuthHub.

## Step 4 — Collect the Installation Keys

List everything installed for the sub-company and record each hub's `installation_key`:

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X GET \
      'https://api.datahub.syncspider.com/apiv1/internal/templates/installed/templates/456' \
      -H 'Authorization: Bearer YOUR_DESK_TOKEN' \
      -H 'Accept: application/json'
    ```
  </Tab>
</Tabs>

Each entry pairs a hub with the sub-company's key for it:

```json
{
  "data": [
    {
      "template_id": 17,
      "company_id": 456,
      "installation_key": "9b2f61aa-4c3e-4d8f-8a1b-2c3d4e5f6072"
    }
  ]
}
```

These keys are what the sub-company's storefront sends in the `installation-key` header — see [Installation Key](/authentication/installation-key).

## Step 5 — Verify With a Settings Call

The definitive smoke test: call a SettingsHub read endpoint using **only** the sub-company's SettingsHub installation key. This request succeeds only if the sub-company exists, the hub is installed, and the key resolves — and fails with `401` if any part of the provisioning did not go through.

<Tabs>
  <Tab title="cURL">
    ```bash
    curl -s -X GET \
      'https://api.datahub.syncspider.com/api/v1/apps/settings-hub/locales' \
      -H 'installation-key: 9b2f61aa-4c3e-4d8f-8a1b-2c3d4e5f6072' \
      -H 'Accept: application/json'
    ```
  </Tab>
</Tabs>

Expected result — `200` with the installation's locales:

```json
{
  "data": [
    { "id": 1, "code": "en", "name": "English", "is_default": true }
  ]
}
```

| Response | Meaning |
|---|---|
| `200` with data | ✅ Sub-company fully provisioned — done. |
| `401` | The installation key does not resolve — the install in step 3 did not complete, or you copied a key from the wrong company. Re-check step 4. |
| `404` | SettingsHub routes not reachable — SettingsHub was not installed for this company. |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `400` "Company can have maximum of N" | Sub-account quota exhausted | Upgrade the parent company's plan. |
| `400` "Company does not support agency features" | Parent is not an agency, or your user has no access to it | Ask your administrator to enable agency features / grant access. |
| `400` "application is already installed" | Re-running step 3 for an installed hub | Not an error — the installation already exists; fetch its key in step 4. |
| Hubs installed into the wrong company | Skipped step 2 | Switch `current_company_id` to the sub-company and reinstall the missing hubs there. |
| `403` on the install call | Token has read-only API permission | Use a token with read/write permission. |

<Update label="2026-10-30" description="Nested content fields for custom themes" tags={["feature", "storefront", "storefront-builder"]}>

## Nested complex and collection fields

- Merchants can nest complex and collection fields (complex → complex → collection, and so on). Each presented field now includes `show_on_storefront` plus picker extras (`html`, `excerpt`, `href`, `hex`, `media`, `items`, recursive `fields` / `rows`).
- New complex / collection fields are hidden on the default shop listing and detail (`show_on_storefront` false). Custom themes still receive every shop-safe field except password and JSON on `entry.fields` and `entry.fields_by_code.{code}`.
- Theme contract: `__content-listing` / `__content-detail` are fixed pages. Include `partials/content-field-value` at any depth (`compact` on the listing). Look a hidden tree up with `fields_by_code`. See [Content types](/advanced/storefront/content-types) and the theme [view-data](/advanced/storefront-themes/view-data) pack.

</Update>

## Content listing — grid, cards, and native links

- Shop listing view data includes `listing_view` (`grid` or `cards` from `?view=`).
- The default theme uses a horizontally scrollable data grid on desktop and a card list on phones. Desktop can switch between the two.

<Update label="2026-10-29" description="Storefront URL rewrites and SEO path generation" tags={["feature", "storefront"]}>

## StorefrontHub — URL rewrites

- **Store Setup → URL Rewrites** — Magento-style redirects on the storefront host (subdomain or custom domain). Paths are locale-stripped; product paths use the `products/` prefix (e.g. `products/old-slug` → `products/new-slug`).
- **Custom and system rules** — Admins create custom 301/302 rows. System rows are recorded when a product/category/page path changes.
- **Generate missing paths** — One action fills empty product `seo.slug`, category `seo.slug`, and Builder `url_key` from name/title (kebab-case). Collisions use `{base}-{id}`. Existing paths are not overwritten. See [StorefrontHub](/hubs/storefront-hub).

<Update label="2026-10-26" description="Sales agents can search a company before choosing a user" tags={["feature", "storefront"]}>

## Storefront — company search for sales agents

- **Company first.** The customer-selection page opens on company search (name, company number, email, or VAT number). Each row is a company. A company with one person who can sign in shows that person's name, and continue shops as that person. A company with several people opens that list so the agent picks one.
- **User search.** A switch on the same page searches people by name, email, or customer number, and the row shows the company name.
- **Who is listed.** A company with nobody who can sign in is hidden. An inactive company is hidden. An agent tied to one company only sees that company.
- **Themes.** The form still posts `customer_id`. New view data: `$searchMode`, `$companies`, `$selectedCompany`. A theme that replaces `pages/customer-selection.blade.php` keeps listing people from `$customers` until that file is updated. See [Page recipes](/advanced/storefront-themes/page-recipes) §10.4.

</Update>

## Rate limiting

- **Two more scopes documented** — `storefront_action` (10/min per shop customer or browser session) for storefront account actions such as generating, rotating or deleting a catalog export, and `embed` (20/min per IP and installation key) for the Integration Hub embed bootstrap and token refresh.

<Update label="2026-10-26" description="Subscription-only products are no longer sold once" tags={["fix", "storefront"]}>

## SubscriptionHub: subscription-only purchase mode

- **Storefront** — products with purchase mode `subscription_only` no longer show a one-time price, tier prices or **Add to cart**. Product cards link to the product page, where the customer subscribes. `one_time_and_subscription` products are unchanged. See [Purchase modes](/hubs/subscription-hub#purchase-modes).
- **Cart and checkout** — the cart API, storefront add to cart, bulk add and quick order refuse a subscription-only product with *"This product is only available as a subscription."* (`422`, `"error": "cart_purchase_restricted"`). A cart that already holds one cannot be checked out. Reorder and accepting a proposal under **My account** skip it.
- **API checkout** — `POST /carts/{cart}/subscription-checkout` accepts an optional `product_id` and `quantity`. The product is subscribed and the cart is left untouched. A repeated request for the same product right after the first one answers `409`, so a double submit never places two orders.
- **Theme contract** — new view variable `$cartRestrictedProductIds`. See [View data](/advanced/storefront-themes/view-data).

</Update>

<Update label="2026-10-25" description="Store fallback payment method" tags={["feature", "storefront"]}>

## Storefront — checkout payment method

- **Store default.** Settings → Configuration → Storefront, Checkout, can name a fallback payment method. It is used only when the shopper has no default of their own on the customer, company, or group, and only when that method is allowed for them.
- **Hide payment method.** When that tick is on and a method could be selected, the bundled checkout does not show the Payment method block. The order still uses the selected method. Another allowed method can still be submitted.
- **Not allowed.** When the store method is not allowed for a shopper who has no default of their own, the payment list stays on the page. Checkout does not stop.
- **Themes.** `$store['default_billing_method_id']` and `$store['hide_payment_method']`. See [View data](/advanced/storefront-themes/view-data) and [StorefrontHub settings](/hubs/storefront-hub).

</Update>

<Update label="2026-10-14" description="Shipping and rule amounts in the cart currency" tags={["improvement"]}>

## Multi-currency — shipping, add-ons and rules

- Shipping method prices, table rates and shipping add-ons are configured in the base currency and now charged in the cart or order currency at the configured exchange rate. Before, a non-base cart was charged the base amount unconverted.
- Cart and catalog price rules compare price thresholds in the base currency and convert fixed discount amounts into the cart or request currency. Rule progress values are reported in the cart currency.
- Admin and MCP-created orders charge the shipping method in the order currency, also when the shipping method is changed later. See [Shipping, Add-ons and Rule Amounts](/core-concepts/pricing#shipping-add-ons-and-rule-amounts).

<Update label="2026-10-11" description="Required theme README, in-place uploads, section overrides" tags={["feature", "storefront"]}>

## Storefront themes — required README, in-place uploads, section overrides

- **Every theme documents itself:** a theme `.zip` must include a root `README.md` with four filled-in sections — *Purpose*, *What this theme changes*, *Scripts and libraries* and *Still on the default theme*. Uploads without it, or with an empty section, are rejected at the manifest step with a message that names the missing sections. An optional `CHANGELOG.md` is kept as well. Both are stored on the version (`readme`, `changelog`) and shown on the theme's page in the admin. See [Theme README and CHANGELOG](/advanced/storefront-themes/theme-readme).
- **Upload into an existing theme:** `POST /themes/{theme}/versions` creates the next version of that theme. An archive whose `theme.json` name belongs to a different theme is rejected.
- **Section overrides:** the default theme has new override points on cart, checkout, favorites, every account page, sign-in, category, guest-order, proposal, customer-selection and error pages. A theme can `@extends('default::pages.cart')` and replace one section, keeping default-theme updates for the rest. See [Blade API](/advanced/storefront-themes/blade-api) §9.0 and the [author checklist](/advanced/storefront-themes/checklist).

</Update>

<Update label="2026-10-02" description="CAPTCHA for public AuthHub endpoints" tags={["feature", "security"]}>

## CAPTCHA on registration, login and storefront forms

- **New AuthHub settings group `captcha`** — Admin: **Settings → Configuration → AuthHub**. Switch it on, pick the provider (Cloudflare Turnstile), paste your own site and secret key, and choose which forms to protect: `login`, `register`, `forgot-password`, `reset-password`, `verify-email`, `resend-verification`, `cms-form`. Off by default, and a missing key keeps it inert.
- **`fail_open`** decides what happens when our server cannot reach the provider: off (default) rejects the submission, on accepts it anyway. A visitor whose browser cannot load the widget is always rejected either way.
- **API clients** send the challenge as `captcha_token` in the body or the `X-Captcha-Token` header; a protected endpoint answers `422` with a `captcha` error without one. `GET /api/v1/apps/auth-hub/captcha-config` returns the provider and site key (never the secret) for clients that render the widget themselves.
- **Storefront themes need no change** — the widget and its script are rendered by the platform on every protected form. Place it yourself with the new `@storefrontCaptcha`, and read `$store['captcha']` if you want your own copy around it. See [Forms](/advanced/storefront-themes/forms) and [AuthHub](/hubs/auth-hub).

</Update>

<Update label="2026-10-01" description="SubscriptionHub renewals and billing settings" tags={["feature"]}>

## SubscriptionHub: renewals and recurring payments

- **New hub page** — [SubscriptionHub](/hubs/subscription-hub) documents product settings, interval units, subscriptions, history, checkout and the status lifecycle.
- **Billing settings** — new `billing` settings group: `billing_collection_mode` (`auto_charge`: charge the card saved at the first checkout; `pay_now_email`: email a payment link for every renewal) and `recurring_provider` (optional single online billing method for automatic charges). Subscription checkout offers only the billing methods the mode allows.
- **Renewal payments** — automatic Stripe / Mollie card charges with hourly retries for temporary errors; payment-link renewals stay open until the next due date (at least 3 days), after which the order is cancelled and the subscription moves to `payment_failed`.
- **Payment link** — public signed `GET /api/v1/apps/subscription-hub/renewal-payment/{installationKey}/{order}` and a seeded NotificationHub email type `subscription_renewal_payment_link`. Never opens a second payment while one is being prepared or processed (409), and stops working once the subscription ended or no longer waits for the order (410). The page answers in the customer's language (English, German).
- **Safer renewals** — an order cancelled in OrderHub while its charge is retried is never charged (`order_closed`); ending a subscription cancels its unpaid renewal order; pausing moves the payment deadline; a card charge still processing at the provider (e.g. SEPA) is checked before the next cycle is ordered (`charge_pending`).

</Update>

<Update label="2026-09-30" description="Company user invitations" tags={["feature", "breaking", "customer-hub"]}>

## Company user invitations

A company administrator can now invite people into their own company from the storefront. The invitee has no account: they open a one-time link, set a password, and join the inviting company with its default role, addresses and permissions.

- **Admin endpoints** — `GET/POST /customer-hub/company-invitations`, `POST .../{id}/resend`, `DELETE .../{id}`. The company is always taken from the caller's shop session, never from the request.
- **Public endpoints** — `GET /customer-hub/{installationKey}/invitations/{token}` to preview and `POST .../accept` to join. No authentication; the invitee has no account yet. Any unusable token returns `410` without saying why.
- **New Settings group** — **Company User Invitations** on CustomerHub: link validity, a cap on pending invitations, the default role, and whether invited users skip admin approval. See [CustomerHub → Settings Groups](/hubs/customer-hub).
- **Email** — new configurable notification types `company_user_invitation` (to the invitee) and `company_user_invitation_accepted` (to the inviter).
- **Audit trail** — every invitation records creation, sending, acceptance, revocation and expiry.

<Callout kind="warning">
**Breaking — a permission grant is required before the feature works.** The storefront permission `storefront.account.manage-users` was previously registered but unenforced. It now gates all four administrator endpoints and **no role holds it by default**, so the endpoints return `403` for everyone until a tenant grants it to whichever role acts as company administrator (Roles → storefront permissions). Nothing else changes for tenants that do not use invitations.
</Callout>

</Update>

## AccountingHub — Bank Reconciliation

- **Auto-match** — `POST /reconciliations/auto-match` scans unmatched bank transactions and links them to open documents when confidence ≥ the configurable threshold (default 0.9) with a clear runner-up gap; runs automatically after every import when enabled. New **Settings → Apps → Accounting Hub** group: `auto_match_enabled`, `auto_match_min_confidence`, `amount_tolerance`.
- **Smarter suggestions** — candidates limited to open documents in the transaction's currency; invoices match on `balance_due`; confidence blends amount, reference, counterparty name, and booking-date proximity.
- **Bank fees on match** — pass `fee_amount` (net settlement): the document settles on the gross `matched_amount`, the fee is stored on the reconciliation and mirrored to the ledger transaction.
- **Documentless classification** — `POST /bank-transactions/{id}/classify` books `bank_fee` / `bank_interest` / `other` without a document so charges leave the unmatched pool with an audit trail.
- **Unmatch** — `DELETE /reconciliations/{id}` removes a wrong link and returns the transaction to the unmatched pool; matching an already-paid invoice is now rejected with 422.
- **Reconciliation report** — `GET /reports/reconciliation` (JSON) and `POST /reports/reconciliation/pdf` per bank account and period: opening/closing balance, credits/debits, fees, matched/classified/unmatched, per-transaction match detail.
- **Currency guards** — imported rows inherit the account currency; cross-currency matches are rejected.

<Update label="2026-06-03" description="Custom Order attributes on checkout" tags={["feature"]}>

## OrderHub × AttributesHub — custom Order attributes on storefront checkout

Tenants can now extend the OrderHub storefront checkout with their own fields without backend changes — purchase order numbers, internal notes, delivery preferences, anything modeled as an AttributesHub attribute.

### How it works

1. Create an Attribute Group of `type = "order"` in AttributesHub.
2. Add attributes inside that group and toggle the new **Use in Checkout** switch (visible on the admin attribute edit page only when the group is of type `order`).
3. The storefront automatically picks them up:
   - `GET /api/v1/apps/order-hub/carts/{cart}/checkout` returns an `available_attributes` array (id, code, name, type, required, group, values, translation) — only attributes with `group.type='order'` AND `use_in_checkout=true`.
   - `POST /api/v1/apps/order-hub/carts/{cart}/checkout` accepts an `attributes` array of `{attribute_id, value, auto_create_value?}` entries; ineligible or missing-required ids return HTTP 422 with explicit messages.

### Persistence

Submitted values are stored polymorphically against the resulting Order (`attributable_type=Apps\OrderHub\Models\Orders`, `attributable_id={order.id}`). Read them back with `?include=attributeValues,attributeValues.value,attributeValues.value.attribute` on order detail endpoints, or via the `$order->{attribute_code}` magic getter.

### Filters

`Attribute` is now filterable by `use_in_checkout` and `use_in_notifications` (in addition to the existing visibility / filtering flags).

See [OrderHub → Checkout flow](/advanced/checkout-flow), [OrderHub hub page](/hubs/order-hub), and [AttributesHub hub page](/hubs/attributes-hub) for the complete contract.

</Update>

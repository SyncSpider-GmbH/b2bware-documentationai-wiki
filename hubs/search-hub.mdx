---
title: SearchHub
description: Typesense search add-on. Mongo search remains the fallback.
---

SearchHub indexes selected hubs into Typesense and serves search, facets, and an embeddable box. Stores without the add-on, and any request Typesense cannot answer in time, use the existing Mongo search.

## Settings

<Expandable title="SearchHub settings reference">

**general** — General

| Setting | Type | Description |
|---------|------|-------------|
| `enabled` | boolean | Turn the add-on on for this store. Off uses Mongo search. |
| `languages` | string | Comma-separated language codes. One collection per language. |
| `typo_tolerance` | boolean | Allow typos. |
| `num_typos` | number | Maximum typos when tolerance is on. |
| `prefix` | boolean | Search-as-you-type. |

**cluster** — Cluster

| Setting | Type | Description |
|---------|------|-------------|
| `host` | string | Typesense admin host. |
| `port` | number | Typesense port. Local Homebrew default is 8108. |
| `protocol` | string | `http` or `https`. |
| `api_key` | secret | Admin API key, stored encrypted. |
| `public_host` | string | Host the browser should use for the embedded search box (production default `search.b2bware.com`). Empty means the admin host. |

**ranking** — Ranking

| Setting | Type | Description |
|---------|------|-------------|
| `query_by_weights` | string | `field:weight` pairs, for example `name:4,sku:3`. |

| `sets` | JSON | Synonym sets applied on the next reindex. |

## Product listings

With the add-on on and Product Hub indexed, the storefront catalog search (`?q=`) and the admin product list search (`filter[search]`) take their matches from Typesense. Status, category, price and stock filters still apply on the catalog data. Without an explicit sort the list keeps the Typesense ranking and later pages continue it; choosing a sort orders the matched products by that field instead. If Typesense does not answer, the request falls back to the catalog's own text search.

## Facets on search pages

On a storefront search page the attribute filters and the category counts in the sidebar are built from the same set of products the search engine matched, so a typo-tolerant or synonym match shows up in the filters exactly as it does in the grid, and a category badge counts the matches inside that category. Category pages and the full catalog keep their usual filters and catalog-wide counts.

## Languages

Each language in `general.languages` gets its own collection. Documents carry the product translation for that language (name, description, category names, attribute labels) and the base value where no translation exists. Storefront searches use the page locale, admin searches the tenant default language. A language that is not indexed, or whose collection is still being built, is answered by the first indexed language.

## Keeping the index current

Saving or deleting a product, its categories, attribute values, prices, stock, translations, media or variant links queues an update of that product's document within a few seconds; several changes to one product in that window become one update. Changing a variant updates its parent. Settings changes that affect the whole index (languages, indexed hubs, synonyms, curation, facet fields) run a full reindex instead.

## Reindex from the admin

Both settings pages (the **Search** entry in the sidebar and **Settings → Apps → Search**) end with a *Search index* panel. It shows whether the search node is reachable, whether a queue worker is running, each indexed hub and language with its document count, and when the last rebuild finished. **Reindex now** rebuilds every indexed collection; while it runs the panel shows a progress bar and the button is disabled, and a second request is refused until the first one finishes. The button needs the *Run a search reindex* permission. A warning appears when nothing is processing the queue, because neither a rebuild nor the incremental updates can run without a worker.

A rebuild never interrupts search: the new index is built next to the current one and only replaces it once every chunk has finished. If a chunk fails, the rebuild stops, the previous index stays in use, and the panel shows *Failed, previous index kept* with the reason. Product changes made while a rebuild runs are written to both indexes, so nothing is lost at the switch.

Synonym sets and pin/hide rules are checked when you save: broken JSON, a missing `id`, a rule without an action, or a pin without a position is refused with a message that names the entry, instead of failing the next rebuild.

## Search box on any site

SearchHub ships a small search widget that runs in the visitor's browser and talks to the search node directly, so a partner site, a landing page or a custom theme can offer the same search as the storefront without going through the store's API.

```html
<div data-searchhub-box
     data-installation="YOUR-SEARCHHUB-INSTALLATION-KEY"
     data-lang="en"
     data-product-url="https://shop.example.com/en/products/{slug}"
     data-currency="EUR"></div>
<script src="https://YOUR-B2BWARE-HOST/api/v1/apps/search-hub/embed.js" defer></script>
```

By default the box renders a full search page: an input, a facet sidebar built from categories and the attributes you index, a result list with image, name, SKU and price, and paging. With `data-mode="dropdown"` and `data-attach="<css selector>"` it instead adds a suggestion panel under existing search inputs, with a *See all results* link that points to `data-results-url`. Other attributes: `data-customer-group` (show that group's prices and visibility), `data-limit`, `data-placeholder`, `data-color` (accent), `data-facets="off"` or a comma-separated list of facet fields, and `data-skip-path` to keep the dropdown off your own results page. The storefront's default theme already mounts the dropdown in its header for stores with SearchHub enabled.

The widget first asks B2Bware for a short-lived search key and only then queries the search node. That key is limited to the store's own collections, to products that are public, and to what the given customer group may see; it cannot change anything and it cannot read another store. Product links use the product's SEO slug, or its id when none is set. Search results are only as fresh as the index, so a product changed moments ago shows up once the incremental sync has run.

## What a product document contains

Name, SKU, description, category names, attribute labels (all in the collection language), variant SKUs, the primary image URL, the regular price and a regular price per customer group, the product's status and URL slug, and the product's visibility. Visibility follows the product permissions set in Product Hub: products visible to everyone, allowed for selected customer groups, or hidden from selected groups. Browser searches with a scoped key only return public products that visitor may see; a signed-in customer's group is part of the key.

## Search API

`GET /api/v1/apps/search-hub/search?q=&lang=en&hub=product-hub&limit=20&page=1`

Response `engine` is `typesense` or `mongo`. `hits` contain `id`, `name`, and `sku`; `found` is the total, `page` echoes the requested page and `lang` names the collection language that served the hits. `lang` in the query is optional and defaults to the request language.

Scoped keys: `POST /api/v1/apps/search-hub/keys`. A key only lists that store's collections.

Index status: `GET /api/v1/apps/search-hub/status` returns `enabled`, `health` (`ok`, `host`), `collections` (`hub`, `lang`, `alias`, `built`, `documents`, `building`), `reindex` (`running`, `started_at`, `batch` with `total_jobs`, `processed_jobs`, `failed_jobs`, `progress`, and `last` with `swapped`, `failed_jobs`, `error`) and `worker` (`state` `alive` | `dead` | `unknown`, `backlog`). `POST /api/v1/apps/search-hub/reindex` queues a full rebuild and answers `409` while one is running.

Public embed (no authentication, rate-limited per IP): `GET /api/v1/apps/search-hub/embed.js` serves the widget; `GET /api/v1/apps/search-hub/embed/{installationKey}/key?customer_group=` returns `key` (scoped search key), `expires_at`, `public_url` (the search node the browser should call), `hubs` (hub → language → collection), `languages`, `default_lang` and `search` (`query_by`, `query_by_weights`, `facet_by`, `num_typos`, `prefix`). `installationKey` may be any of the store company's installation keys (the storefront's or the SearchHub one). It answers `404` when the company has no SearchHub or the add-on is off and `503` when no key can be issued. `GET /api/v1/apps/search-hub/public/search?installation=&q=` is the server-side variant for pages that cannot call the search node directly; it only returns public products visible to everyone.

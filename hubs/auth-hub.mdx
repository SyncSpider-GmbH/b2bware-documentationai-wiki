## Overview

AuthHub issues and manages user sessions. It is the entry point for storefront
customers and for sales agents who impersonate a customer. With Unified
Contacts enabled, the selected company is stored on the login/session and drives
company-scoped storefront access.

**Base URL:** `api/v1/apps/auth-hub/`

<Callout kind="info">
Most endpoints sit behind `auth:api`. The two public flows — `reset-password` and `verify-email` — use the installation key in the URL instead of a bearer token, because the user is not logged in yet.
</Callout>

## Endpoints

<Tabs>
  <Tab title="Session" icon="key">

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| POST | `/login` | `auth:api` | Exchange credentials for a personal access token. |
| POST | `/register` | `auth:api` | Create a new customer account. |
| POST | `/logout` | `auth:api` | Revoke the current token. |
| POST | `/refresh` | `auth:api` | Refresh the current authenticated session. |
| POST | `/logout-all` | `auth:api` | Revoke all sessions for the current customer. |
| GET  | `/me` | `auth:api` | Return the authenticated user and current company context. |
| GET | `/me/sessions` | `auth:api` | List active sessions with company and impersonator metadata. |
| DELETE | `/me/sessions/{id}` | `auth:api` | Revoke one owned session. |

`GET /me/sessions` returns `{ "data": [...] }`. Each session includes the
existing `id`, `ip`, `location`, `last_used_at`, `login_date`, and `current`
fields plus:

| Field | Type | Meaning |
|---|---|---|
| `user_account_id` | integer or `null` | Canonical Unified Contacts user-account ID attached to the login. |
| `active_company_id` | integer or `null` | Company selected for this session; `null` is the B2C/no-company context. |
| `impersonator` | integer or `null` | User-account ID of the sales agent that created an impersonated session. |

  </Tab>
  <Tab title="Company Context" icon="building">

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| GET | `/me/companies` | `auth:api` | List active company memberships and current `active_company_id`. |
| PUT | `/me/active-company` | `auth:api` | Switch the current login/session to an accessible active company, or `null` for B2C context. |

`/me` preserves the compatibility customer fields. When Unified Contacts is
enabled it additionally returns `memberships`, `active_company_id`, and
`user_account_id`. Company affiliations describe commercial relationships only;
they never grant access. Authorization comes from active, currently valid
company memberships.

Switching company changes the current session context. It does not rewrite
existing carts, quotes, or orders, whose `company_id` values are immutable
creation-time snapshots.

## Company-Aware Impersonation

`POST /impersonate/{customerId}` accepts optional `active_company_id`. It is
required when the target has more than one company. A multi-company agent must
also select an active agent company first, and the agent and target must share
access to the selected company. The issued login records both
`active_company_id` and the impersonator user-account ID for audit and session
listing.

## Company-Context Permission Rollout

After enabling Unified Contacts authorization on an existing installation, run:

```bash
php artisan auth-hub:sync-company-context-permissions
```

Use `--installation-key=<uuid>` to target one AuthHub installation; without it,
the command discovers and processes all active AuthHub installations. The
command fails without making changes when Unified Contacts authorization is
disabled or no installation can be resolved.

The rollout is additive and idempotent. It adds
`auth-hub.company-context.view` and
`auth-hub.company-context.switch` only to eligible storefront role types
(`user` and `agent`), preserves every existing custom grant or revocation, and
invalidates changed role-permission caches. Re-running it reports zero updates
once those permissions are present.

The AuthHub package seeder invokes the same synchronization service during a
normal package install/update pass. While Unified Contacts authorization is
disabled, the seed stays pending and changes nothing; a later package pass
applies it after authorization is enabled. After a successful sync the seed is
marked complete. The underlying additive synchronization is idempotent and safe
to retry; neither the seeder nor command recomputes a role's complete defaults
or grants unrelated back-office permissions.

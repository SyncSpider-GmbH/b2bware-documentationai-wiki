## Overview

SubscriptionHub lets customers subscribe to a product and receive it again at a fixed interval (every 2 weeks, every month, …). The merchant configures which products can be subscribed, at which intervals and prices; every renewal is placed as a regular [OrderHub](/hubs/order-hub) order.

**Base URL:** `api/v1/apps/subscription-hub/`

<Callout kind="info">
Subscriptions are created only by a signed-in storefront customer at checkout (product page or the API checkout below). There is no admin endpoint that creates a subscription; admins manage existing ones.
</Callout>

## Concepts

| Entity | Purpose |
|---|---|
| **Product settings** | Per product: enabled flag, purchase mode (`subscription_only`, `one_time_and_subscription`), offered intervals `{unit, count, price, active}`, optional max cycles, price policy (`locked` or `current`). Variants use the setting of their configurable parent. |
| **Interval units** | Extendable list of units (`day`, `week`, `month`, `year`). A unit used by product settings or live subscriptions cannot be deleted, deactivated or renamed (409). |
| **Subscriptions** | One per subscribed product. Snapshots interval, price, quantity, addresses and billing / shipping method at checkout. |
| **History** | Append-only audit log of every lifecycle event (`created`, `renewed`, `renewal_paid`, `paused`, `resumed`, `cancelled`, `ended`, `payment_failed`, `address_updated`, `updated`, `status_changed`). |

### Status lifecycle

| Status | Meaning |
|---|---|
| `pending` | The first order is waiting for its online payment. Nothing renews yet; the subscription becomes `active` when the order is paid and `ended` if that payment fails or the order is cancelled. Invoice / on-account orders start `active` at once. |
| `active` | Renews at every due date. |
| `paused` | No renewals. Resuming moves the next due date by the paused time. |
| `cancelled` | Pending cancel: no more renewals, but the current period runs out, then the subscription ends. Can be undone before the period ends. |
| `payment_failed` | Renewals are halted until an admin resumes, cancels or ends the subscription. `last_error.reason` explains why. |
| `ended` | Terminal. |

```text
                first payment arrives
 checkout ──► pending ─────────────────► active ◄────────────── resume ─────────┐
                 │                       │ │ │                                  │
   first payment │                 pause │ │ │ renewal not collected            │
   fails / order │                       ▼ │ ▼                                  │
   cancelled     │                  paused │ payment_failed ────────────────────┤
                 │                    │  │ │       │                            │
                 │                    │  │ │cancel │                            │
                 │                    │  │ ▼       ▼                            │
                 │                    │  └─► cancelled ─── undo cancel ─────────┤
                 │                    │          │                              │
                 │                    └──────────┼───────── resume ─────────────┘
                 │                               │ period runs out
                 ▼                               ▼
               ended ◄───── end (admin, assistant or max_cycles reached, from any live status)
```

| From | Allowed transitions |
|---|---|
| `pending` | `active` (first payment), `ended` |
| `active` | `paused`, `cancelled`, `payment_failed`, `ended` |
| `paused` | `active` (resume), `cancelled`, `ended` |
| `payment_failed` | `active` (resume), `cancelled`, `ended` |
| `cancelled` | `active` (undo cancel), `ended` |
| `ended` | none |

Invoice / on-account checkouts skip `pending` and start `active`. Every arrow writes a history entry and raises the matching [webhook event](#webhook-events).

An admin action on a subscription that is being renewed at that moment answers **409**; retry shortly.

### Customer account

Signed-in customers manage their subscriptions on the storefront under **My account → Subscriptions** (`/{locale}/account/subscriptions`). The sidebar entry appears once the customer has a subscription.

- The page lists only the customer's own subscriptions with product, interval, quantity, price per delivery, status and the next delivery (or end) date.
- **Cancel subscription** is offered for `active`, `paused` and `payment_failed` subscriptions. The subscription moves to `cancelled`: it no longer renews and ends at the end of the period already paid for. The history entry records the customer as the actor (`impersonated` when a sales agent shops as them).
- An unpaid payment-link renewal shows **Pay now** (the same payment page as the email) until the payment deadline. This also applies after a cancel: the customer keeps the current period only by paying that renewal; otherwise it is cancelled at the deadline and the subscription ends.
- Themes may restyle the page with `modules/subscription-hub/account-subscriptions.blade.php`; the cancel button is the `subscription-cancel` [form type](/advanced/storefront-themes/forms).

## Settings

**billing** — how renewal orders are paid.

| Setting | Type | Default | Description |
|---|---|---|---|
| `billing_collection_mode` | select | `auto_charge` | `auto_charge`: the card the customer saved at the first checkout is charged automatically at every renewal. `pay_now_email`: every renewal order is created unpaid and the customer gets an email with a payment link. |
| `recurring_provider` | select (billing method) | none | Optional. In `auto_charge` mode, the only online billing method offered at subscription checkout. Only billing methods whose provider supports automatic charges (Stripe, Mollie) can be chosen. |

Which billing methods subscription checkout offers:

| Billing method | `auto_charge` | `pay_now_email` |
|---|---|---|
| Invoice / on account (no provider) | yes | yes |
| Online provider with automatic charges (Stripe, Mollie) | yes — the card is always saved at the first payment; only the `recurring_provider` when one is set | yes |
| Other online providers | no | yes |

## Renewals

An hourly scheduler renews every subscription whose next due date has passed. Each renewal is a regular OrderHub order (marked `meta_data.subscription_renewal`) for the subscription's customer, at the locked subscription price — or, with price policy `current`, the product setting's current interval price. Coupons and automatic cart price rules never apply, and renewals are placed even when the product is out of stock.

How the order is paid depends on the billing method and the collection mode:

| Case | What happens |
|---|---|
| Invoice / on account | The order is placed; nothing is collected online. |
| `auto_charge` with a saved card | The saved card is charged. A decline sets `payment_failed` and cancels the order. |
| `pay_now_email`, or `auto_charge` without a saved card | The order is placed unpaid and the customer is emailed a payment link (NotificationHub type `subscription_renewal_payment_link`). |

```text
 hourly scheduler: active subscriptions whose next_due_at has passed
 (cancelled ones too, while a payment link is open)
        │
        ▼
 previous payment link unpaid? ── before its deadline ─► wait
        │ no / paid                 deadline passed ─────► order cancelled, payment_failed
        ▼
 max_cycles already reached? ──── yes ─► ended
        │ no
        ▼
 previous card charge processing? ── yes ─► wait (failed at the provider ─► payment_failed)
        │ no
        ▼
 place the renewal order in OrderHub ── fails ─► retried hourly (24×), then payment_failed
        │
        ├─ invoice / on account ──► nothing collected online ──────────────┐
        ├─ payment link ──────────► link emailed ──────────────────────────┤
        └─ saved card ────────────► charge off-session                     │
                                       ├─ paid / processing ───────────────┤
                                       ├─ declined ─► order cancelled,     │
                                       │              payment_failed       │
                                       └─ provider error ─► retried hourly │
                                                   (24×), then payment_failed
                                                                           ▼
             history `renewed` + webhook subscriptionhub.subscription.renewed;
             next_due_at moves one interval

 a payment link paid in time records `renewal_paid` (when the order is paid,
 or at the next run if the payment event was missed)
```

**Payment links.** The customer has until the next due date — and at least 3 days after the email — to pay. Until then no further renewal order is placed. If the order is still unpaid after the deadline, it is cancelled and the subscription moves to `payment_failed` (`renewal_unpaid`); a resume orders that cycle again. A customer who never received the email is not halted; sending is retried at every run. Pausing moves the deadline by the paused time; ending the subscription cancels the unpaid order and closes its payment link.

**Pending card charges.** A charge the provider accepted but has not confirmed yet (e.g. SEPA Direct Debit) is checked at the provider when the next cycle falls due. Paid: the next cycle renews. Still processing: the next cycle waits (`charge_pending`). No live payment any more: the order is marked failed and the subscription moves to `payment_failed` (`charge_failed`). Cancelled in OrderHub meanwhile: `payment_failed` (`order_closed`). If the provider cannot be reached at all, the check is retried hourly and the subscription halts with `charge_unresolved` once the attempts run out; check the payment at the provider before resuming.

**Temporary problems** (order creation failed, payment provider unreachable) keep the subscription active and are retried every hour for up to 24 attempts, then the subscription moves to `payment_failed`. A card charge is never repeated while an earlier attempt may have gone through: when the provider's answer cannot be confirmed, the subscription halts with `charge_unresolved` and keeps the order. Check the payment at the provider before resuming.

### Failure reasons (`last_error.reason`)

| Reason | Meaning |
|---|---|
| `price_unavailable`, `product_unavailable` | The product or its price can no longer be ordered. |
| `address_missing`, `method_missing`, `customer_unavailable` | The snapshotted address, billing / shipping method or customer is gone, disabled or no longer belongs to the customer. |
| `charge_failed` | The card was declined (`decline_code` from the provider when available), or no saved card can be charged any more (`decline_code` = `payment_method_unavailable`). |
| `charge_unavailable`, `order_failed` | Temporary; retried hourly. A provider answering that the same charge is still in flight counts as temporary. |
| `order_closed` | The renewal order was cancelled or refunded in OrderHub before its payment was collected or confirmed. It is never charged; a resume orders the cycle again. |
| `charge_unresolved` | The charge result could not be confirmed after all retries (also for a pending charge the provider could not be asked about). |
| `renewal_unpaid` | A payment-link renewal was not paid before its deadline. |
| `payment_link_unsent` | The payment-link email could not be sent yet; retried at every run (no halt). |
| `charge_pending` | The previous cycle's card charge is still being processed by the provider (e.g. SEPA); the next cycle waits for it (no halt). |

## Webhook events

Every history entry raises an EventHub event that merchants can subscribe a webhook to. The delivery's `data` is the subscription after the change; `meta` carries the history entry (`history_type`, `actor`, `details`). Full table and payload notes: [Webhooks → SubscriptionHub events](/core-concepts/webhooks#per-hub-event-reference).

| History entry | Event slug |
|---|---|
| `created` | `subscriptionhub.subscription.created` (plus `activated` when it starts active: invoice / on-account, or an online order already paid) |
| `resumed` from `pending` (first payment arrived) | `subscriptionhub.subscription.activated` |
| `renewed` | `subscriptionhub.subscription.renewed` |
| `renewal_paid` | `subscriptionhub.subscription.renewal_paid` |
| `paused` / `resumed` / `cancelled` / `ended` | `subscriptionhub.subscription.paused` / `resumed` / `cancelled` / `ended` |
| `payment_failed` | `subscriptionhub.subscription.payment_failed` |
| `address_updated`, `updated` | `subscriptionhub.subscription.updated` |

`status_changed` entries raise no event. A failing webhook listener never undoes the change that raised it.

## MCP tools

AI assistants connected through the [MCP Server](/ai-tools/mcp-server) can read and manage subscriptions:

| Tool | Permission | What it does |
|---|---|---|
| `list_subscriptions` | `subscription-hub.subscriptions.view` | Paginated list (newest first) with customer, company and product names; filter by `status`, `customer_id`, `company_id`, `product_id`. |
| `get_subscription` | `subscription-hub.subscriptions.view` | One subscription with addresses, method ids, dates, open renewal orders and the last error. |
| `list_subscription_history` | `subscription-hub.history.view` | The history of one subscription, newest first. |
| `pause_subscription`, `resume_subscription`, `cancel_subscription`, `end_subscription` | `subscription-hub.subscriptions.update` | The lifecycle actions above with the same transition rules; optional `reason` (max 500 characters). |

Status changes are written to the history with the authorizing user as actor and `via: "mcp"`, and raise the same webhook events as the admin. Payment tokens are never returned. An operator without `subscription-hub.subscriptions.view` only reaches their own subscriptions; anything else answers like a missing subscription.
